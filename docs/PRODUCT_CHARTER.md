# SRW 产品宪章 · Governance G1

状态：**ACTIVE POLICY**；生效后所有新开发必须遵守。治理制度版本 G1 不是软件产品版本，也不代表 GA。版本细则在 VERSION_POLICY.md。

## 1. 使命

在保留成熟招聘业务与证据链的前提下，将 SRW 从复杂原型转化为可以实际处理招聘事务、易于理解、可恢复且可验证的软件产品。首个目标交付为 **Windows EXE + 本地 HTML/Browser 两种入口**，共用一个 SRW Core 和相同的数据、业务规则与审计。

产品竞争方向不是盲目扩展功能数量，而是让招聘决策和后续行动更透明、正确、高效。

## 2. 不可妥协的 A 类产品不变量

A1. 人类控制候选人推进与录用/Offer 决策；AI 输出只能辅助，不能自动产生权威 HumanDecision。
A2. Source、Claim、事实核实、Judgment、Decision Context、历史记录必须有来源和版本关系；材料/Criteria 更新时，旧决策不得冒充当前有效决策。
A3. 缺失证据与否定事实必须区分；冲突证据不得自动静默取舍。
A4. 保护 v0.8.12-R2 对照中有实际价值的业务能力：岗位与标准、候选人、Evidence、Interview/Scorecard、Decision、Offer、运营跟进、Knowledge、AI/OCR/ASR、备份恢复。可重构实现，但必须有功能映射、迁移和行为等价验收。
A5. 本地数据为权威数据，候选人材料/SQLite/密钥不可意外进入源码、CI、构建工件或诊断日志；隐私默认最小化。
A6. Windows 与 HTML/Browser 的正式版本共享同一个权威 Core、业务状态和审计语义，不维护两套相互同步的“真相”数据库。
A7. 源码可运行、API PASS、浏览器 PASS、Windows GUI PASS、整包可发布是不同等级；禁止把未验证能力宣传成已验收。
A8. 用户现有工作区不得被构建、测试、升级或探索程序静默打开、修改或覆盖。

A 类变更必须有用户作为产品负责人的明确决定、可追踪 ADR、迁移与回退方案、特定回归测试，不能由 Agent 自行突破。

## 3. B 类当前发行承诺

B1. 完整纵向招聘业务闭环及主要异常路径都能实际从 UI 操作。
B2. Windows Native 候选完整装配、可启动、正常退出、稳定运行，并能备份、恢复、重启、升级。
B3. 本地 HTML/Browser 与 Windows 并行开发和独立验收，共用同一个权威 Core，解决会话、冲突、后台任务所有权。
B4. 保留并实测 AI Provider、OCR、ASR、Knowledge、人工核实与源证据展示能力；失败有清晰降级。
B5. 版本、运行环境、Schema、源码 SHA、独立工件 SHA、发行门禁信息可追溯。
B6. 提供用户能理解的安装/启动、业务使用、数据恢复和错误诊断文档。

B 类可选择不同的技术实现，但变更必须说明行为及验收影响；不为“赶进度”宣称通过。

## 4. C 类 Agent 自主实现空间

局部组件优化、模块拆分、缓存/查询优化、修复脚本、测试夹具、内部代码组织，在不违反 A/B 约束时 Agent 可自主推进，仍须 PR、CI 和回归证据。

## 5. 明确的非目标

本阶段不开展：全新 UI 设计体系、全新招聘业务内核重写、云端登录、SaaS、多租户、庞大企业合规平台、重型微服务基础设施、全自动招聘决定、纯静态 HTML 冒充全功能产品。最小必要的本地 API 安全控制、数据处理合法性和保护机制仍然必须实施。

## 6. 产品验收的价值排序

**防止数据/证据/决策损坏 > 核心业务可完成 > 安全恢复和可靠运行 > 清晰可用性 > 性能效率 > 非必要新功能。**

在问题竞争时先关闭实际阻断问题，而不是为了显示功能增长增加新页面。

## 7. 产品负责人决策边界

- 需要负责人：修改 A 类不变量、删除既有成熟业务能力、引入全新产品形态/云依赖、改变根本数据权威策略、决定正式 RC/GA。
- Agent 可推进：B 类中的已批准实现细节与 C 类工作，按任务契约、回归和 PR 审核操作。
- 任何重大例外进入 docs/decisions/ADR-*.md；注明背景、方案、替代选项、证据、回退和重新讨论条件。

## 8. 验收与真实用户研究顺序

先用合成/经授权去识别数据完成内部端到端产品验收；首个可用产品建立后，再安排真实招聘人员试用，验证效率、正确性和使用感受。不能以暂缓用户研究为由跳过内部质量测试。
